## Summary

This PR adds user authentication functionality using JWT (JSON Web Tokens). It implements secure login/logout endpoints, token validation middleware, and user session management. The authentication system is designed to be scalable and follows industry best practices for token-based authentication.

- `src/auth/logout.ts`: Implements logout functionality with token invalidation

## Testing

To test the authentication functionality:

1. **Login with valid credentials**
   - Send POST request to `/api/auth/login` with valid username and password
   - Verify response contains JWT token
   - Check token is valid and contains correct user information

2. **Login with invalid credentials**
   - Send POST request to `/api/auth/login` with invalid credentials
   - Verify response returns 401 Unauthorized
   - Check error message is appropriate

3. **Token validation middleware**
   - Access a protected route without token
   - Verify response returns 401 Unauthorized
   - Access protected route with valid token
   - Verify request succeeds and user context is available

4. **Logout functionality**
   - Send POST request to `/api/auth/logout` with valid token
   - Verify token is invalidated
   - Attempt to use invalidated token
   - Verify subsequent requests fail with 401

5. **Session management**
   - Test token refresh mechanism
   - Verify session expiration after timeout
   - Check concurrent session handling

## Breaking Changes

- **API endpoint changes**: The authentication endpoints have changed from `/api/login` to `/api/auth/login`. Existing clients will need to update their API calls.
- **Token format**: JWT tokens now use a different signing algorithm (RS256 instead of HS256). Token validation logic has been updated accordingly.
- **Middleware integration**: Protected routes now require authentication middleware to be explicitly configured. Previously unprotected routes may now require authentication.

## Context for Reviewers

### Design Decisions

- **JWT over sessions**: Chose JWT tokens over session-based authentication for better scalability and statelessness. This allows the application to scale horizontally without shared session storage.

- **Token expiration**: Access tokens expire after 1 hour for security. Refresh tokens expire after 24 hours to balance security and user experience.

- **Password hashing**: Using bcryptjs with a cost factor of 10 for password hashing. This provides a good balance between security and performance.

- **Middleware design**: Authentication middleware is designed to be flexible and can be applied to individual routes or globally. This allows for both public and protected endpoints.

### Trade-offs

- **Token size**: JWT tokens are larger than session IDs, which increases request size. This is acceptable given the benefits of statelessness.

- **Token revocation**: JWT tokens cannot be easily revoked before expiration. Implemented a token blacklist to handle this edge case when necessary.

- **Refresh token storage**: Refresh tokens are stored in the database for validation. This adds a small amount of state but is necessary for security.

### Performance Considerations

- Token validation is fast (sub-millisecond) using RS256 with cached public keys
- Password hashing is intentionally slow (bcrypt) to prevent brute force attacks
- Database queries for refresh tokens are indexed for optimal performance

### Security Considerations

- All passwords are hashed using bcrypt with salt
- Tokens are signed using RS256 asymmetric keys
- HTTPS is required for all authentication endpoints
- Token expiration limits the window for token theft
- Refresh tokens are single-use and rotated on each refresh
